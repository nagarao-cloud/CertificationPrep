<a name="eli12"></a>
## 1. Explain like I'm 12

Imagine a warehouse so big it can never run out of space, run by robots
that never lose anything you hand them. You don't get an aisle number —
you just write a label on the box (the **key**) and hand it over, and any
time you say the label again, the robots find it instantly, whether you
have 10 boxes or 10 trillion. You can tell the robots "if a box hasn't
been touched in 30 days, move it to the cheap slow storage in the back,"
or "if someone tries to throw this box away, don't actually let them for
90 days" (that's a legal hold), or "keep a perfect copy of every box in a
warehouse in a different city, automatically." That warehouse is Amazon
S3. Almost everything else in this exam — Glue, Athena, Redshift Spectrum,
EMR — is just a smarter way of *reading* boxes from this warehouse.

<a name="technical"></a>
## 2. Explain technically

Amazon S3 (Simple Storage Service) is an object storage service, not a
filesystem and not a block store. Data is stored as **objects** (a blob of
bytes up to 5 TB, plus metadata) inside **buckets**, addressed by a flat
**key** namespace — "folders" in the console are a UI illusion; the key
`raw/2026/08/09/events.parquet` is one string, not a directory tree. S3 is
**Regional**, replicates synchronously across a minimum of three
Availability Zones within the Region (except the S3 One Zone-IA and S3
Express One Zone classes, which trade that AZ redundancy for lower cost or
lower latency), and is designed for **11 nines (99.999999999%) of
durability** per object per year and up to **99.99% availability**
depending on storage class. It has no provisioning step, no shard count,
no node count — capacity and throughput scale automatically per-prefix.
For a data platform, S3 is simultaneously: the landing zone for raw
ingested data, the curated/transformed data lake, the source and target
for ETL (Glue, EMR, Athena CTAS), the destination for exported analytics
(DynamoDB export, Redshift UNLOAD), and — via S3 Tables and Redshift
Spectrum/Athena — a queryable analytical store in its own right.

<a name="senior"></a>
## 3. Explain like a Senior AWS Data Engineer

A senior engineer treats S3 design as three separate, ordered decisions,
because getting the order wrong is expensive to unwind later. **First,
key design** — the prefix structure decided on day one determines
partition pruning efficiency for every Athena/Redshift Spectrum query for
the life of the bucket; renaming millions of keys later is a real
migration project, not a config change. **Second, storage-class and
lifecycle strategy** — decided *after* you understand the access pattern,
not before; moving data to Glacier that a nightly batch job still reads
turns a $0.023/GB storage saving into a $0.03–$0.09/GB-per-restore
penalty that dwarfs it. **Third, table format** — whether the curated
zone is plain Parquet files, Iceberg-on-general-purpose-S3 (self-managed
table maintenance), or **S3 Tables** (AWS-managed Iceberg maintenance).
This third decision is now genuinely load-bearing for DEA-C01: the exam
expects you to know that S3 Tables removes the operational burden of
compaction, snapshot expiration, and orphan-file cleanup that a
self-managed Iceberg lake on general-purpose S3 requires someone to run
(via a Glue job, EMR job, or open-source maintenance procedures). A
senior engineer picks S3 Tables specifically when the pain point named in
the scenario is "our Iceberg tables are accumulating small files and
nobody owns compaction" — not because Iceberg itself requires it.

## 4. Production architecture

```
                         PRODUCERS
        ┌───────────────┬───────────────┬───────────────┐
        │  Glue ETL job │  DMS (CDC)    │ Amazon Data    │
        │  writes       │  writes       │ Firehose       │
        │  Parquet      │  raw CDC JSON │ delivers batch │
        └───────┬───────┴───────┬───────┴───────┬───────┘
                │               │               │
                v               v               v
        ┌─────────────────────────────────────────────────────┐
        │             S3 BUCKET — RAW / BRONZE PREFIX           │
        │  s3://lake/raw/source=orders/year=2026/month=08/...   │
        │  SSE-KMS encrypted · versioning ON · lifecycle to IA  │
        └───────────────────────┬───────────────────────────-──┘
                                 │  Glue job / EMR job reads,
                                 │  cleans, dedupes, converts
                                 v
        ┌─────────────────────────────────────────────────────┐
        │           S3 — CURATED / SILVER PREFIX                │
        │  Parquet, partitioned by date + key business dims     │
        │  OR an S3 Tables bucket (managed Iceberg)              │
        └───────────────────────┬───────────────────────────-──┘
                                 │  read by
                 ┌───────────────┼───────────────┐
                 v               v               v
            Athena          Redshift         EMR / Glue
          (partition       Spectrum /       (further
           projection)     data sharing      aggregation)
                 │               │               │
                 └───────────────┴───────────────┘
                                 │
                                 v
                    CRR to a second Region (DR) +
                    Object Lock on compliance prefixes
```

Reading the diagram: three different producer patterns (Glue batch,
DMS CDC, Amazon Data Firehose streaming) all converge on a **raw/bronze
prefix** — this is the pattern the exam calls "land everything in S3
first," because S3 is durable, cheap, and decouples ingestion speed from
transformation speed. A transformation job (Glue or EMR) reads the raw
prefix, cleans and deduplicates, and writes a **curated/silver prefix**
either as plain partitioned Parquet or as an **S3 Tables** bucket if ACID
transactions and managed compaction are required. Three different
consumption engines — Athena, Redshift Spectrum, and EMR/Glue for further
aggregation — read the curated layer without any data movement, because
S3 is the shared storage layer all compute engines point at (this is the
core "storage/compute separation" idea the exam tests repeatedly).
Wrapped around the whole bucket: **Cross-Region Replication** feeds a
second Region for disaster recovery, and **Object Lock** is applied to
any prefix holding data under a compliance retention requirement.

<a name="classes"></a>
## 5. Storage classes — the cost/retrieval table

| Storage class | Min duration | AZs | Retrieval | Relative storage $/GB-mo | Retrieval fee | Use case |
|---|---|---|---|---|---|---|
| **S3 Standard** | none | ≥3 | Milliseconds | Highest (baseline) | None | Frequently accessed, active data lake curated zone |
| **S3 Intelligent-Tiering** | none | ≥3 | Milliseconds | Baseline + small monitoring fee/object | None (auto-tiers) | Unknown or changing access patterns |
| **S3 Standard-IA** | 30 days | ≥3 | Milliseconds | ~45% less than Standard | Per-GB retrieval fee | Backups, DR secondary, monthly reports |
| **S3 One Zone-IA** | 30 days | 1 | Milliseconds | ~20% less than Standard-IA | Per-GB retrieval fee | Easily-recreatable data, secondary copies |
| **S3 Express One Zone** | none | 1 | **Single-digit ms** (fastest) | Higher than Standard, but far fewer requests needed | Lower per-request cost | Latency-sensitive analytics, ML training reads, high-TPS Athena/Redshift Spectrum scans |
| **S3 Glacier Instant Retrieval** | 90 days | ≥3 | Milliseconds | ~68% less than Standard | Per-GB retrieval fee | Quarterly-accessed archives that still need instant reads |
| **S3 Glacier Flexible Retrieval** | 90 days | ≥3 | Minutes (expedited) to hours (standard/bulk) | Cheaper than Instant Retrieval | Retrieval fee, tiered by speed | Archives accessed a few times a year |
| **S3 Glacier Deep Archive** | 180 days | ≥3 | 12 hrs (standard) / 48 hrs (bulk) | Lowest of all classes | Retrieval fee | Compliance archives, 7-year retention, rarely if ever read |

**How to read this for the exam:** the table is ordered from fastest+
most expensive to slowest+cheapest. Every exam question about storage
class is really asking "where does the *access frequency and required
retrieval latency* named in the scenario land on this table" — not "what
is the cheapest class," because the cheapest class with an unacceptable
retrieval latency is a wrong answer even if the question says "minimize
cost."

⚠️ **S3 Express One Zone is single-AZ** — it trades the standard
multi-AZ durability model for speed. Never propose it for data that must
survive an AZ failure without being reproducible elsewhere.

<a name="lifecycle"></a>
## 6. Lifecycle policies

Lifecycle rules are prefix- or tag-scoped and do two independent things:
**transition** actions (move an object to a cheaper class after N days)
and **expiration** actions (delete an object, or a previous version,
after N days). A typical data-lake lifecycle rule chain:

```
Day 0     → object written to S3 Standard (raw/bronze zone)
Day 30    → transition to S3 Standard-IA (still queried occasionally)
Day 90    → transition to S3 Glacier Instant Retrieval (rarely queried,
             but a downstream job might still need instant access)
Day 365   → transition to S3 Glacier Deep Archive (compliance retention only)
Day 2555  → expire (delete) — 7-year retention satisfied
```

Lifecycle rules also expire **noncurrent versions** (old versions created
by overwrites, when versioning is on) and can be scoped separately from
current-version rules — a common exam scenario is "our bucket size keeps
growing even though we delete old files," and the answer is that
versioning is retaining every prior version with no noncurrent-version
expiration rule.

⚠️ **Minimum storage duration charges apply even if you delete or
transition early.** Moving a Standard-IA object to Glacier at day 25
(before the object's own IA minimum was satisfied) still incurs the
30-day IA charge. Lifecycle transitions should respect each class's
minimum duration or the cost math breaks.

<a name="versioning"></a>
## 7. Versioning

Versioning keeps every write to a key as a separate, retrievable version
instead of overwriting in place; a "delete" with versioning on doesn't
erase data — it inserts a **delete marker**, and the object is recovered
by removing the marker. Versioning is required for **Cross-Region
Replication**, **Object Lock**, and is the mechanism that protects
against accidental overwrite/delete — including a compromised or
misconfigured pipeline job that reprocesses and overwrites the raw zone.
It is off by default and, once enabled, cannot be fully disabled — only
suspended (new writes stop creating versions, but existing versions
remain).

<a name="replication"></a>
## 8. Replication (CRR / SRR)

| | Cross-Region Replication (CRR) | Same-Region Replication (SRR) |
|---|---|---|
| Purpose | Disaster recovery, data residency, latency reduction for global readers | Log aggregation, compliance copies with a different storage class/account, dev/test data sync |
| Requirement | Versioning enabled on source and destination | Versioning enabled on source and destination |
| Async or sync | Asynchronous (typically seconds, SLA under RTC is 15 min for 99.99%) | Asynchronous |
| Can replicate across accounts | Yes (with a bucket policy/IAM role) | Yes |
| Replication Time Control (RTC) | Optional add-on for an SLA-backed replication time | Optional |

Replication is **not retroactive** by default — it applies only to
objects written after the rule is created (existing objects need S3
Batch Replication to backfill). Replication does not replicate
**delete markers** unless explicitly configured to, which is a common
exam trap: "we deleted objects in the source bucket and they're still in
the destination" is expected behavior, not a bug.

<a name="objectlock"></a>
## 9. Object Lock (WORM)

Object Lock enforces write-once-read-many at the object-version level,
required for regulatory retention (SEC 17a-4, FINRA, HIPAA-adjacent
retention mandates). It requires versioning and must be enabled **at
bucket creation** (cannot be turned on for an existing bucket after the
fact — it can only be enabled at creation, or via a support request in
narrow cases). Two modes:

- **Governance mode** — protected from overwrite/delete by everyone
  except users with the `s3:BypassGovernanceRetention` permission.
  Suitable for internal retention policy enforcement.
- **Compliance mode** — protected from deletion by **everyone,
  including the AWS account root user**, until the retention period
  expires. This is the mode regulators actually require; it cannot be
  shortened or bypassed by anyone.

A **legal hold** is a separate, independent lock with no expiration date
— it stays until explicitly removed, regardless of any retention period,
and is the mechanism for "preserve this data for ongoing litigation."

⚠️ **Object Lock compliance mode is genuinely immutable — even the
account owner cannot delete or shorten it before expiry.** If a scenario
says "must be tamper-proof against all users including administrators,"
that phrase specifically means compliance mode, not governance mode.

<a name="consistency"></a>
## 10. Consistency model

Since December 2020, S3 provides **strong read-after-write consistency**
for all operations, including new object PUTs, overwrite PUTs, and
DELETEs — a GET or LIST immediately after a successful write always
reflects the latest state. There is no longer an "eventual consistency"
caveat to design around (this used to be a real gotcha with overwrite
PUTs pre-2020, and old material or old exam questions may still test the
outdated eventual-consistency model — do not trust source material that
describes S3 as eventually consistent for overwrites).

<a name="multipart"></a>
## 11. Multipart upload

Objects over 5 GB **must** use multipart upload; AWS recommends it for
anything over 100 MB because it uploads parts in parallel, retries only
the failed part (not the whole object) on a network error, and can start
before the full object even exists on the client side (useful for
streaming uploads). Key numbers: minimum part size 5 MB (except the last
part), maximum part size 5 GB, maximum 10,000 parts, maximum object size
5 TB. Incomplete multipart uploads accumulate storage charges for the
uploaded-but-never-completed parts — a lifecycle rule
(`AbortIncompleteMultipartUpload`) should clean these up automatically;
forgetting this rule is a common real-world (and exam) cost leak.

<a name="s3tables"></a>
## 12. S3 Tables — managed Iceberg storage

**What it is:** S3 Tables is a purpose-built S3 bucket type
(`s3tables`) that stores data specifically as **Apache Iceberg tables**
and — unlike self-managed Iceberg on a general-purpose S3 bucket — AWS
automatically runs the background table-maintenance operations that
Iceberg tables need to stay performant: **compaction** (merging small
files produced by frequent small writes into larger ones), **snapshot
expiration** (removing old snapshots per the table's retention policy),
and **unreferenced/orphan file cleanup** (deleting files no live
snapshot points to, which otherwise silently accumulate storage cost).
S3 Tables buckets integrate directly with the **AWS Glue Data Catalog**
(each table registers automatically) and are queryable from Athena,
Redshift, EMR, and Glue without extra configuration — the same engines
that query self-managed Iceberg tables.

### S3 Tables vs. self-managed Iceberg on general-purpose S3

| | Self-managed Iceberg on general-purpose S3 | S3 Tables |
|---|---|---|
| Compaction | You schedule and run it (Glue job, EMR job, or manual `OPTIMIZE`) | Automatic, managed by AWS |
| Snapshot expiration | You schedule and run it | Automatic, managed by AWS |
| Orphan file cleanup | You schedule and run it | Automatic, managed by AWS |
| Catalog registration | Manual (Glue crawler or explicit DDL) | Automatic on table creation |
| Bucket type | Any general-purpose S3 bucket | Dedicated table bucket type |
| Query engines | Athena, Redshift, EMR, Glue (all Iceberg-aware engines) | Same engines |
| Throughput at high transaction rates | Can degrade if maintenance is neglected | Designed for consistently higher sustained TPS on small-object writes |
| Best fit | Teams that already own Iceberg maintenance tooling, or need a non-table use case in the same bucket | Teams whose pain point is "nobody owns compaction," or a high-frequency streaming-ingest table workload |

⚠️ **Exam framing:** if a scenario says an Iceberg-on-S3 data lake has
degraded query performance from an accumulation of small files and the
team has no dedicated pipeline to run compaction, S3 Tables is the
"least operational overhead" answer — not "write a Lambda function on a
schedule to run `OPTIMIZE`." That second answer is what you'd do on a
general-purpose bucket; the exam-preferred, newer answer removes the
need entirely.

<a name="requestcost"></a>
## 13. Request cost structure

S3 bills separately for **storage** (per GB-month, by class) and
**requests** (per 1,000 requests, by operation type and class) plus
**data transfer out** to the internet (transfer *in* is free; transfer
between S3 and most AWS compute in the same Region is free). Request
pricing is tiered by operation cost to AWS, not flat:

| Operation group | Relative cost | Examples |
|---|---|---|
| PUT / COPY / POST / LIST (writes + listing) | Higher per-1,000 | `PutObject`, `CompleteMultipartUpload`, `ListObjects` |
| GET / SELECT (reads) | Lower per-1,000 | `GetObject`, `HeadObject`, `S3 Select` |
| Lifecycle transition requests | Billed per object transitioned | Glacier transitions in particular |
| Data retrieval (IA/Glacier tiers only) | Per-GB, tiered by speed | Expedited > Standard > Bulk |

**Exam-relevant cost implication:** a workload with millions of tiny
objects and frequent LIST operations (the "small file problem," see next
section) pays disproportionately in request costs even when total data
volume is small — this is one of the two costs (the other being query
engine overhead) that motivate file-size/partitioning best practices.

<a name="partitioning"></a>
## 14. Partitioning strategy and the small-file problem

Partitioning means encoding filterable columns into the S3 key prefix —
e.g., `s3://lake/curated/year=2026/month=08/day=09/region=us-east/...` —
so that query engines (Athena, Redshift Spectrum, EMR) can **prune**
partitions and skip scanning objects that can't match the query's `WHERE`
clause, without reading their content. Two failure modes the exam tests:

- **Too few, too large partitions** (e.g., partitioning only by year) —
  a query for one day still scans a full year of data; poor pruning.
- **Too many, too small files** (the "small file problem") — a
  streaming job flushing every few seconds can produce millions of
  kilobyte-sized objects. Query engines pay a fixed per-file overhead
  (open, read footer/metadata, close) that dominates runtime when files
  are small, and S3 LIST/GET request costs scale with file count, not
  data volume. The standard fix is a **compaction job** (Glue, EMR, or
  automatic if using S3 Tables/Iceberg) that periodically merges small
  files into targets in the 128 MB–1 GB range, plus choosing a
  partition granularity that yields files in that range for the given
  ingest rate — daily partitions for a low-volume source, hourly for a
  high-volume one.

⚠️ **Exam trap:** "reduce query latency and cost on a data lake with
millions of small Parquet files" points to compaction/repartitioning
(or migrating to S3 Tables), not to a bigger Athena workgroup limit or a
faster storage class — the bottleneck is file count, not throughput.

<a name="encryption"></a>
## 15. Encryption options

| Option | Who manages the key | Key material visible to AWS | Use case |
|---|---|---|---|
| **SSE-S3** (`AES256`) | AWS-managed, S3-owned | N/A | Default; encryption at rest with zero setup |
| **SSE-KMS** | Customer-managed or AWS-managed KMS key | AWS KMS holds it; access is logged and IAM/key-policy controlled | When you need an audit trail of every decrypt (CloudTrail) and per-key access control |
| **DSSE-KMS** (dual-layer) | Customer-managed or AWS-managed KMS key | Two independent encryption layers | Regulatory requirements mandating two layers of encryption (e.g., certain FIPS/compliance regimes) |
| **SSE-C** (customer-provided key) | Customer supplies the key on every request; AWS never stores it | Not stored by AWS at all | Customer wants full key custody; AWS never persists it — customer must resend the key on every GET |

⚠️ **SSE-KMS at high request volume can hit KMS API rate limits**
(requests-per-second quota on the KMS key), which is a real production
and exam gotcha for high-throughput streaming writes — the fix is
S3 Bucket Keys (a data-key caching feature that reduces KMS API calls
per object) or, if truly not needed, SSE-S3.

<a name="whentouse"></a>
## 16. When to use / when NOT to use

**Use S3 when:** you need durable, cheap, virtually unlimited object
storage as the foundation of a data lake; you need a shared storage
layer multiple compute engines (Athena, Redshift Spectrum, EMR, Glue)
read without moving data; you need to decouple ingestion rate from
processing rate by landing raw data first; you need tiered
cost/retrieval trade-offs over the data's lifetime.

**Do NOT use S3 when:** you need low-latency **row-level** transactional
updates at high frequency for an OLTP application — that's DynamoDB or
RDS/Aurora, not S3 (S3 Tables narrows this gap for analytical Iceberg
writes, but it is still not a transactional OLTP store); you need a
POSIX filesystem with file locking semantics for a legacy application —
that's EFS or FSx; you need sub-millisecond key-value lookups at massive
scale — that's DynamoDB or DAX.

<a name="advlim"></a>
## 17. Advantages and limitations

**Advantages:** 11 nines durability; virtually unlimited scale with no
provisioning; pay-for-what-you-use; storage-class tiering for automatic
cost optimization; strong read-after-write consistency; deep native
integration with every AWS analytics and ML service; S3 Tables closes
the Iceberg-maintenance operational gap.

**Limitations:** not a filesystem (no native file locking, no partial
in-place byte-range writes — the whole object is replaced); 5 TB max
object size; eventual settling time for lifecycle transitions (not
instant); LIST performance and cost degrade with extreme small-file
counts unless compacted; cross-Region replication is asynchronous, not
synchronous (RPO is not zero).

<a name="perfscale"></a>
## 18. Performance, scaling, and high availability

S3 scales request rate **per prefix**, not per bucket: each prefix can
sustain roughly 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests
per second, and S3 automatically scales beyond that as traffic grows —
but a workload that concentrates all traffic under one narrow prefix
(e.g., a single date prefix used by every writer) can throttle even
though the bucket overall has huge headroom; spreading writes across
more prefixes (or using randomized/hashed key prefixes for extreme
throughput needs) raises the effective ceiling. High availability comes
from synchronous multi-AZ replication within the Region for all classes
except One Zone-IA and Express One Zone; for cross-Region resilience,
CRR is the mechanism, with an asynchronous RPO.

<a name="security"></a>
## 19. Security

Defense in depth: **IAM policies** (identity-based, what a principal can
do), **bucket policies** (resource-based, who can access this bucket),
**S3 Block Public Access** (account- and bucket-level override that
should be left ON by default for a data lake), **VPC endpoints**
(gateway endpoint for S3 keeps traffic off the public internet from
within a VPC, at no per-hour cost), **Access Points** (named,
scoped-down access paths for shared buckets with many consumer teams —
each team gets a policy scoped to their access point rather than
editing one giant bucket policy), and **encryption at rest** (SSE-S3/
SSE-KMS/DSSE-KMS/SSE-C, see above) plus **TLS in transit**. For
governance at scale across many buckets and accounts, **AWS Lake
Formation** layers table- and column-level permissions (LF-Tags) on top
of the underlying S3 permissions.

<a name="failures"></a>
## 20. Failure scenarios and common mistakes

- **Overwriting the raw/bronze zone in place with no versioning** — a
  bad reprocessing job corrupts source-of-truth data with no way back.
  Fix: versioning on, and treat bronze as append-only.
- **No `AbortIncompleteMultipartUpload` lifecycle rule** — failed or
  abandoned multipart uploads silently accrue storage charges forever.
- **Public Access Block disabled "temporarily" and forgotten** — the
  single most common real-world data-lake exposure incident.
- **Replicating without a plan for delete markers** — assuming CRR
  mirrors deletes when the rule wasn't configured to.
- **Using SSE-KMS on a very high-throughput stream without S3 Bucket
  Keys enabled** — hitting KMS request-rate limits under load.
- **Partitioning by a high-cardinality, rarely-filtered column** (e.g.,
  `user_id`) instead of the columns queries actually filter on (date,
  region) — produces excessive tiny partitions with no pruning benefit.

<a name="examtraps"></a>
## 21. Exam traps

⚠️ **"Cheapest storage" without a retrieval-latency requirement is a
trap answer waiting to happen.** Always check whether the scenario
implies the data must still be *readable quickly* — if so, Glacier Deep
Archive is disqualified even though it's the cheapest number on the
table.

⚠️ **Object Lock cannot be added to an existing bucket after the fact**
(only enabled at creation, with narrow support-ticket exceptions) — a
scenario that says "we need to add WORM protection to our existing
production bucket" is testing whether you know this requires creating a
new bucket and migrating data, not flipping a setting.

⚠️ **Governance mode vs. compliance mode** — "tamper-proof against
administrators" = compliance mode. Anything less strict = governance
mode. Confusing these two is one of the most common wrong-answer
patterns on Object Lock questions.

⚠️ **S3 is strongly consistent since Dec 2020** — do not pick an answer
that adds artificial delay-and-retry logic to "work around S3's eventual
consistency." That workaround is no longer necessary and picking it
signals outdated knowledge.

⚠️ **S3 Tables vs. plain S3 + Iceberg** — if the pain point is
maintenance overhead (compaction/snapshot cleanup), S3 Tables is the
answer. If the scenario doesn't mention Iceberg or table maintenance at
all, don't reach for S3 Tables reflexively — plain S3 + Parquet is still
correct for a simple, non-transactional lake.

<a name="interview"></a>
## 22. Interview questions

- *"How would you design the S3 key structure for a data lake ingesting
  from 50 different source systems?"* Strong answer: a
  `<zone>/<source>/<year>/<month>/<day>/<hour if high-volume>/<files>`
  structure — zone first for lifecycle/IAM scoping by bronze/silver/gold,
  source next for per-source access control and schema evolution
  isolation, then date partitioning aligned to the source's actual
  ingest volume (daily for low-volume, hourly for high-volume) so
  compacted file sizes land in the 128 MB–1 GB sweet spot.
- *"A team says their S3 costs doubled after they started using
  versioning. Why, and what would you check?"* Strong answer: every
  overwrite now keeps the old version billed as full storage; check for
  a missing noncurrent-version expiration lifecycle rule, and check
  whether a job is overwriting the same keys far more often than
  expected (a bug, not a versioning problem per se).
- *"When would you choose S3 Tables over Iceberg on general-purpose
  S3?"* Strong answer: when nobody on the team owns Iceberg table
  maintenance and small-file/snapshot bloat is degrading query
  performance — S3 Tables shifts that operational burden to AWS.

<a name="cheatsheet"></a>
## 23. Cheat sheet

| If the scenario says... | Reach for... |
|---|---|
| frequently accessed, active data | S3 Standard |
| unknown/changing access pattern | S3 Intelligent-Tiering |
| accessed monthly, need instant reads | S3 Standard-IA / Glacier Instant Retrieval |
| lowest cost, compliance archive, rarely read | S3 Glacier Deep Archive |
| lowest latency, high-TPS analytics reads | S3 Express One Zone |
| regulatory WORM, tamper-proof from everyone | Object Lock, compliance mode |
| WORM but admins can still override | Object Lock, governance mode |
| DR / multi-Region durability | Cross-Region Replication |
| Iceberg without maintenance overhead | S3 Tables |
| millions of small files, slow queries | Compaction job / repartition / S3 Tables |
| KMS request limits hit on high-throughput writes | Enable S3 Bucket Keys |
| >100 MB upload | Multipart upload |

<a name="mnemonics"></a>
## 24. Memory tricks

**"SIWO"** for storage-class thinking, in order of what to check first:
**S**peed needed → **I**A eligible (30-day min)? → **W**ORM/compliance
needed? → **O**ne-zone acceptable (is loss of the AZ tolerable)?
**"Bronze never changes"** (shared with Domain 1) — the raw S3 zone is
append-only; that's what makes replay possible. **"Compliance can't be
undone, Governance can"** — the one-line way to remember Object Lock
modes.

## 25. Practice questions (15)

**Q1.** A media company stores 200 TB of raw video ingest in S3 Standard.
Videos are transcoded within 24 hours and the raw files are never read
again after transcoding, but compliance requires keeping them for 3
years in case of a dispute. What lifecycle strategy minimizes cost while
meeting the requirement?

A) Delete the raw files after transcoding; recreate from backups if needed
B) Transition to S3 Glacier Deep Archive after 24–48 hours, expire after 3 years
C) Keep everything in S3 Standard for the full 3 years
D) Transition to S3 Standard-IA after 24 hours and never expire

**Answer: B.** The files are effectively never read after transcoding, so
the cheapest class is correct, and there's no instant-access requirement
named — Deep Archive's 12–48 hour retrieval is acceptable for a rare
dispute. (A) violates the compliance retention requirement outright. (C)
ignores the "minimize cost" requirement entirely. (D) is far more
expensive than Deep Archive for data that's essentially never read.

**Q2.** Which encryption option should be used when a customer requires
that AWS never has access to the unencrypted key material at any point,
and the customer will manage key distribution themselves?

A) SSE-S3
B) SSE-KMS
C) SSE-C
D) DSSE-KMS

**Answer: C.** SSE-C means the customer supplies the encryption key on
every request; S3 encrypts/decrypts with it but never stores it. (A) and
(D) both involve AWS-managed key material (S3-owned or KMS-held,
respectively) — the opposite of the requirement. (B) also stores the key
in KMS, which is visible to AWS's key management service.

**Q3.** A data engineering team's Iceberg tables on a general-purpose S3
bucket have degraded query performance due to accumulated small files
from a continuous streaming ingest job, and no one on the team currently
runs compaction. What is the least-operational-overhead fix?

A) Schedule a nightly Lambda function to call Iceberg's OPTIMIZE procedure
B) Migrate the tables into an S3 Tables bucket
C) Increase the Athena workgroup's data-scanned limit
D) Switch the curated zone from Parquet to ORC

**Answer: B.** S3 Tables automatically runs compaction, snapshot
expiration, and orphan-file cleanup — it removes the operational
ownership problem stated in the scenario. (A) technically works but
requires the team to own and maintain that Lambda function — not
"least overhead." (C) treats a symptom (query cost) without fixing the
file-count root cause. (D) doesn't address small-file accumulation at
all.

**Q4.** An application needs strict, tamper-proof retention on financial
records such that not even the AWS account root user can delete them
before a 7-year retention period expires. Which S3 feature and mode
satisfies this?

A) Object Lock, governance mode
B) Bucket policy with an explicit Deny on s3:DeleteObject
C) Object Lock, compliance mode
D) MFA Delete

**Answer: C.** Compliance mode blocks deletion/overwrite for every
principal, including the root user, until retention expires — and it
cannot be shortened by anyone. (A) governance mode can be bypassed by a
principal with `s3:BypassGovernanceRetention`, including potentially the
root user via IAM. (B) a Deny policy can be edited or removed by an
account admin at any time — not tamper-proof. (D) MFA Delete protects
against accidental/malicious deletes with MFA but is not a retention
mechanism and can be disabled by an authorized user.

**Q5.** A team observes that PUT throughput to their S3 bucket throttles
under load even though total account-level S3 usage is far below any
published service quota. What is the most likely cause?

A) The bucket has exceeded its total storage limit
B) All writers are using the same narrow key prefix, concentrating requests
C) SSE-S3 encryption is rate-limiting requests
D) The bucket needs to be moved to a different Region

**Answer: B.** S3 scales request rate per key prefix; concentrating
writes under one narrow prefix can hit the per-prefix request-rate
ceiling even though the bucket overall has enormous headroom.
Distributing keys across more prefixes resolves it. (A) S3 has no
meaningful total storage limit for this purpose. (C) SSE-S3 has no
request-rate impact (unlike SSE-KMS, which can hit KMS API limits, a
different mechanism). (D) Region choice doesn't fix a prefix
concentration problem.

**Q6.** Which is true about S3's consistency model for a `PUT` that
overwrites an existing object, as of the current model?

A) Reads may return stale data for up to a few seconds after the overwrite
B) Reads may return either the old or new version indefinitely until cache expiry
C) A subsequent GET always returns the latest version immediately (strong consistency)
D) Consistency depends on the storage class chosen

**Answer: C.** S3 has provided strong read-after-write consistency for
all operations, including overwrite PUTs, since December 2020. (A) and
(B) describe the old (pre-2020) eventual-consistency model, which no
longer applies. (D) consistency behavior does not vary by storage class.

**Q7.** A cost review finds that a bucket with only 500 GB of actual data
is generating unexpectedly high request charges. Investigation shows
millions of objects each only a few KB in size. What is the primary
driver of the excess cost, and the standard fix?

A) The storage class is wrong; switch to Intelligent-Tiering
B) Request costs scale with object count, not data volume; the fix is compaction
C) Enable Transfer Acceleration to reduce request overhead
D) Enable Cross-Region Replication to spread request load

**Answer: B.** PUT/GET/LIST pricing is per-1,000-requests, so millions
of tiny objects generate request costs disproportionate to the small
data volume — the small-file problem. The fix is a compaction job (or
S3 Tables for Iceberg workloads) to merge small objects into larger
ones. (A) storage class doesn't address request-count costs. (C) and
(D) are unrelated features that don't reduce request count.

**Q8.** Which statement about S3 Cross-Region Replication (CRR) is
accurate?

A) CRR is synchronous and provides a zero RPO
B) CRR requires versioning enabled on both source and destination buckets
C) CRR automatically replicates objects that existed before the rule was created
D) CRR always replicates delete markers by default

**Answer: B.** Versioning must be enabled on both buckets for CRR to
work. (A) CRR is asynchronous — RPO is not zero (Replication Time
Control can bound it with an SLA, but it's still not synchronous). (C)
replication is not retroactive; S3 Batch Replication is needed to
backfill pre-existing objects. (D) delete-marker replication must be
explicitly enabled — it is not the unconditional default behavior.

**Q9.** An upload workflow for large (20 GB) files intermittently fails
partway through due to unreliable client network connections, forcing a
full re-upload each time. What S3 feature addresses this most directly?

A) S3 Transfer Acceleration
B) Multipart upload
C) S3 Select
D) Requester Pays

**Answer: B.** Multipart upload splits the object into independently
uploaded, independently retryable parts — a network failure only
requires re-uploading the failed part, not the whole 20 GB object;
it's also mandatory above 5 GB. (A) Transfer Acceleration speeds up
transfer over long geographic distances but doesn't solve resumability.
(C) S3 Select filters data within an object during retrieval — unrelated
to uploads. (D) Requester Pays shifts billing to the requester —
unrelated to reliability.

**Q10.** A regulated healthcare company needs every decrypt operation
against S3 objects containing PHI to be individually logged with the
identity of the caller, for audit purposes. Which encryption choice
satisfies this most directly?

A) SSE-S3
B) SSE-KMS
C) SSE-C
D) Client-side encryption with a locally managed key never sent to AWS

**Answer: B.** SSE-KMS routes every encrypt/decrypt through AWS KMS,
which logs each call (including caller identity) to CloudTrail —
satisfying the audit requirement natively. (A) SSE-S3 uses S3-owned
keys with no per-call audit trail of decrypts. (C) SSE-C keys aren't
managed by AWS at all, so there's no centralized KMS audit log. (D)
removes AWS visibility entirely, which is the opposite of what's needed
for an AWS-native audit trail.

**Q11.** Which S3 storage class should be avoided for the sole copy of
business-critical data that must survive the loss of an entire
Availability Zone?

A) S3 Standard
B) S3 Standard-IA
C) S3 One Zone-IA
D) S3 Glacier Flexible Retrieval

**Answer: C.** One Zone-IA (and S3 Express One Zone) intentionally store
data in only one AZ to reduce cost — losing that AZ can mean losing the
data, so it's unsuitable as a sole copy of critical data. (A), (B), and
(D) all replicate synchronously across a minimum of three AZs within the
Region.

**Q12.** A Glue job that writes to a raw S3 prefix has a bug and
overwrites production data with malformed output. The team wants the
ability to recover the previous good version of the affected objects.
What should have been enabled beforehand?

A) S3 Object Lock in governance mode
B) S3 Versioning
C) S3 Transfer Acceleration
D) S3 Intelligent-Tiering

**Answer: B.** Versioning retains every prior version of an object on
overwrite, so recovery is simply retrieving the previous version. (A)
Object Lock adds retention/WORM enforcement but the recovery capability
itself comes from versioning, which Object Lock requires as a
prerequisite anyway. (C) and (D) are unrelated to version recovery.

**Q13.** In an Athena-queried S3 data lake partitioned as
`s3://lake/curated/year=2026/`, analysts report that a query filtering
on a specific day still scans an entire year of data. What is the most
likely cause and fix?

A) Athena engine version is outdated; upgrade to Engine v3
B) The partition granularity is too coarse; add month/day partitions (or use partition projection)
C) The bucket needs Intelligent-Tiering enabled
D) S3 Select should be used instead of Athena

**Answer: B.** Partitioning only by year means Athena can prune only
down to a year's worth of data for any query — adding finer-grained
month/day partitions (or partition projection with the right pattern)
lets Athena prune to the actual date range needed. (A) engine version
doesn't affect partition pruning granularity. (C) storage class is
unrelated to query scan scope. (D) S3 Select operates within a single
object and doesn't solve prefix-level pruning.

**Q14.** A company needs to keep an exact, continuously up-to-date copy
of its S3 data lake in a second AWS Region for disaster recovery, and
wants the replication itself to require no custom code. What should they
configure?

A) A scheduled Lambda function that copies new objects nightly
B) S3 Cross-Region Replication with versioning enabled on both buckets
C) AWS DataSync scheduled hourly
D) S3 Transfer Acceleration between the two buckets

**Answer: B.** CRR is the native, no-code, near-continuous
(asynchronous, typically seconds to minutes) replication mechanism
built for exactly this. (A) works but is custom code and only as fresh
as the last run — more operational overhead than a managed feature. (C)
DataSync is built for hybrid/on-prem transfer and scheduled sync, not
the standard answer for bucket-to-bucket continuous replication. (D)
Transfer Acceleration speeds up client uploads over distance; it isn't
a replication mechanism.

**Q15.** Which of the following is an accurate operational difference
between S3 Tables and Apache Iceberg tables stored on a general-purpose
S3 bucket?

A) S3 Tables cannot be queried by Athena, only by Redshift
B) S3 Tables does not support the Iceberg table format at all
C) S3 Tables automates compaction, snapshot expiration, and orphan-file cleanup; general-purpose S3 Iceberg tables require you to run or schedule that maintenance yourself
D) S3 Tables charges no storage or request fees

**Answer: C.** That automated maintenance is the defining operational
difference the exam tests. (A) S3 Tables is queryable by Athena,
Redshift, EMR, and Glue — the same Iceberg-aware engines as
general-purpose S3. (B) S3 Tables *is* Iceberg storage, purpose-built for
it. (D) S3 Tables still bills for storage and requests like any S3
bucket type.
